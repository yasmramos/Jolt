# Project Analysis: Lua / LuaJIT Architecture — Strengths and Improvement Opportunities

Status: baseline analysis for a project that mirrors the Lua 5.4 + LuaJIT 2.x architecture.
All code, comments and documentation in this repository must be written in English
(see `CONVENTIONS.md`). Commits must follow Conventional Commits on the `develop` branch.

## 1. Reference architecture overview

### Lua 5.4 (reference implementation)
- **Front-end**: hand-written recursive-descent parser (`lparser.c`) producing bytecode for a register VM.
- **VM**: optimized register-based interpreter (`lvm.c`) with jump table; instruction format iABC/iABx/iAsBx.
- **Runtime**: incremental mark & sweep GC with generational mode; string interning (short strings); full closures with upvalues captured on heap when needed; C API with registry, weak tables (`__mode`), `__gc`/`__close` semantics, coroutines as first-class light/dark threads.
- **Numbers**: one numeric type family (integers + IEEE754 doubles) with careful int/float coercion rules.
- **Standard libs**: pure-C libraries (base, string, table, math, utf8, io, os, package).

### LuaJIT 2.x (reference JIT)
- **IR layer**: SSA-based trace IR (`lj_ir.h`) built directly from bytecode by the VM loop (no AST round-trip).
- **Tracing JIT**: records hot loops into linear traces, side traces for branches, compiled by a backend-native two-pass assembler (x64 primary; ARM64/ARM partial).
- **Runtime integration**: shadow state (`lua_State` split into fast/slow fields), typed `TValue` with NaN-boxing, FFI library generating native calls at runtime, internalized libc/math, coroutine-aware trace exit machinery, GC integrated with machine-code write barriers.
- **Compatibility**: deliberately frozen at Lua 5.1 semantics.

## 2. Known weaknesses of the reference architecture (our improvement targets)

| # | Area | Problem in Lua/LuaJIT | What we can do better | Priority |
|---|------|------------------------|------------------------|----------|
| A | JIT coverage | Trace JIT fails on dynamic code: `pairs()` over mixed tables, metamethod-heavy loops, many trace exits → falls back to interpreter ("trace abort", "NYI") | Add a **method-tier / region-based tiered compilation** fallback so non-traceable hot code still gets native speed | High |
| B | Optimizer depth | LuaJIT does minimal LICM, no real escape analysis, limited alias analysis | Build passes on the SSA IR: **LICM, range-check elimination, escape analysis + scalar replacement, unrolling with profile-guided bounds** | High |
| C | Type feedback | Types inferred only at record time; polymorphic loops recompile constantly | Profile-guided **type feedback with speculative specialization and automatic deopt/recompilation** | High |
| D | Safe deoptimization | Trace exits are correct but expensive; OSR granularity is coarse | First-class **deopt points embedded in IR**, materialized from a single snapshot representation shared by all tiers | High |
| E | GC pauses | Lua's incremental GC has write-barrier overhead; LuaJIT's is specialized but hard to extend | **Region-based allocation for short-lived objects** (strings from `string.format`, temporaries) + keep M&S as mature generation; make pause targets measurable | Medium |
| F | String/format cost | Interning is good, but `string.format`/concat allocate every call | SIMD-assisted formatting; interned-result caching for constant formats; rope-like concat for chains | Medium |
| G | Table part types | Array/hash split tuned for classic patterns; poor for struct-like tables | Optional **shape maps (hidden classes)** for object-shaped tables → field access becomes constant offsets, enabling unboxed storage | Medium |
| H | Toolchain / ABI | No stable ABI between Lua minor versions; extensions break on upgrade | Define a **stable C ABI layer** (versioned API table) so modules survive upgrades | Medium |
| I | Security posture | Default libs expose `os.execute` etc.; LuaJIT CVE history is mostly JIT/GC memory-safety bugs | Hardened defaults (capability flags for os/io), **memory-safety review gates** on IR/backend, fuzz harnesses (see §4) | High |
| J | Debug/prod tension | Debug hooks slow the VM even when unused; profiling requires patches | Always-on cheap sampling via **code-metadata maps** generated by each tier; zero cost when disabled | Low |
| K | Upstream drift | LuaJIT frozen at 5.1; modern Lua features absent | Decide explicitly: target **Lua 5.4 semantics** and offer 5.1-compat as a lint/mode layer instead of a fork | Medium |
| L | Portability | Backend quality uneven across archs (x64 great, ARM weaker) | Keep IR backend-agnostic; add a **portable baseline tier** (template JIT or high-quality interpreter loop) before optimizing per-arch | High |

## 3. Architectural recommendations for our implementation

1. **Tiered execution pipeline**: interpreter → baseline tier → optimizing tier, all fed by one bytecode and one SSA IR. This keeps Lua's simplicity while capturing LuaJIT's wins and covering its blind spots (A, C, D, L).
2. **Keep the register bytecode.** It is the single best decision in Lua's design; do not deviate without measured justification.
3. **NaN-boxing TValue** like LuaJIT, but design the boxing layout early (it is nearly impossible to change later). Document invariants next to the type tags.
4. **Snapshot-based deopt from day one.** LuaJIT retrofitted complexity here; making the IR the source of truth for recoverable state simplifies every tier.
5. **FFI compatibility strategy**: if exposing native calls, generate them from declarations at runtime like LuaJIT, but verify argument layouts through the stable ABI layer (H) to avoid the class of bugs behind several LuaJIT CVEs.
6. **Profile everything**: build a benchmark suite (see §4) before optimizing; every performance claim in commits/PRs must cite a benchmark delta.

## 4. Verification & benchmark plan
- **Correctness**: official Lua conformance tests + LuaJIT test suite where compatible.
- **Benchmarks**: Shenanight, LuaJSPerf, mandelbrot/nbody/k-nucleotide ports; track interpreter vs baseline vs optimizing tier.
- **Fuzzing**: grammar-based fuzzer for the parser (target: no crashes); structure-aware fuzzer for the IR→asm path (ASAN/UBSAN builds mandatory in CI).
- **Regression gates**: perf budget per tier checked in CI on x64 and ARM64.

## 5. Suggested roadmap slices (each = feature branch off `develop`)
1. `feat(core): bytecode VM + register allocator baseline` (foundation, no JIT yet)
2. `feat(jit): SSA IR builder from bytecode + trace recorder`
3. `feat(jit): x64 backend with snapshot/deopt framework` (D before B/C)
4. `feat(runtime): region allocator + GC integration` (E)
5. `feat(analysis): LICM, escape analysis, bounds-elimination passes` (B)
6. `feat(vm): shape-map tables` (G)
7. `chore(ci): fuzz + benchmark gates` (§4)
